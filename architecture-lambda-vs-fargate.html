2. Option A — Fargate (closest to today)

Each Spring Boot module stays a container. AWS runs them for you. Kafka + Postgres become managed services.

Why Fargate fits this codebase

  • Your services are already long-running Spring Boot apps.
  • Kafka consumers (delivery, allocation, notification, image-analysis) need to stay awake.
  • Least rewrite — mostly packaging + config + managed Kafka/DB.

3. Option B — Lambda-first (big rewrite)

HTTP pieces become functions. Event pieces stop using “Kafka consumer in a JVM” and move to queues/buses — or stay off Lambda.

Why pure Lambda fights this codebase

  • Half your design is Kafka + after-commit publish + idempotent consumers — that assumes processes that stay up.
  • 8 Spring Boot apps ≠ 8 Lambdas without rewriting packaging, startup, and messaging.
  • Cold starts + JPA + many micro-hops can be slower and more expensive than a few Fargate tasks at low traffic.

Rule of thumb for this repo: put request/response and scheduled work on Lambda; keep event consumers and heavy Spring services on Fargate until you replace Kafka.

6. If you pick one next step

  1. Deploy path: Dockerize the 8 services → Fargate + one shared RDS oms + MSK Serverless or Kafka on ECS.
  2. Lambda experiment: only move POST /api/catalog/scrape to a scheduled Lambda writing to S3 — prove the pattern without touching Kafka.
  3. Do not try to lift Spring Cloud Gateway + all Kafka consumers onto Lambda in one go.
