Order Management System

Design overview — drop-shipping fulfillment platform (Java · Spring Boot · Kafka · Angular · AI image matching)

Overview

Customers submit orders through a web app (and, in a later milestone, a mobile app). Administrators record manual bulk purchases from external platforms, receive and allocate bulk units to customer order lines, and track each order through a constrained lifecycle with dual delivery timing. When an order is delivered, the customer is notified.

The system is decomposed into scalable Spring Boot microservices (Java 21), one per bounded context, fronted by an API Gateway and connected by an Apache Kafka event backbone. A dedicated Image Analysis Service performs AI-based visual product matching for image-specified order lines. Clients are an Angular mobile-first web app; a mobile app is a planned later client reusing the same gateway and APIs.

Design Goals

Atomic writes — every rejected submission persists nothing, enforced inside a single JPA transaction per service.
Allocation safety — allocations can never exceed received bulk quantity or requested customer quantity.
Deterministic lifecycle — order status only advances through defined, guarded transitions with a durable, append-only history.
Auditable timing — delivery durations are non-negative whole seconds from a single anchor date.
Eventing — after a successful DB commit, services publish domain events directly to Kafka via DomainEventPublisher.
Horizontal scalability — stateless services scale out via Kubernetes and consume Kafka in consumer groups with idempotent handlers.

Request Flows

Intake

Order submission

Client calls the gateway; for image lines the image is validated, stored, and an ImageUploaded event is published for AI matching. On confirmation, intake validates all lines and calls order-service in one transaction; OrderCreated drives status Created.

Allocation

Bulk purchase → allocate

Admin records a bulk purchase atomically. Received units are logged and allocations created under both guards. When all lines are fully allocated, OrderFullyAllocated moves the order to Allocated.

Delivery

Deliver → notify

Delivery marks record timestamps, compute durations, and guard double-marking. Marking an order delivered sets Delivered_To_Customer and emits NotificationRequested, triggering the customer notification within 60s with retry.

Consumer Scalability & Idempotency

Consumer groups

Each service consumes as a named group; adding replicas increases parallelism up to the partition count.

Partitioning

Topics keyed by aggregate id (orderId, bulkPurchaseId, imageId) so events for one aggregate stay ordered on one partition.

Idempotent handlers

Consumers dedupe on a processed-event table, so at-least-once redelivery is a safe no-op — underpinning guarded single-shot delivery.

Image Analysis Flow (AI)

The Image Analysis Service performs AI-based visual product matching for order lines specified by image. The concrete model sits behind a pluggable VisionProvider interface so it can be swapped without touching callers.

public interface VisionProvider {
    // Returns candidate item matches with confidence scores for an uploaded image.
    List<ItemCandidate> matchProduct(ImageRef image);
}

public record ItemCandidate(String itemRef, double confidence) {}  // confidence in [0, 1]
  1. intake-service validates the image (JPEG/PNG, ≤10 MB), stores it, and publishes ImageUploaded.
  2. image-analysis-service consumes it, loads the image, and calls VisionProvider.matchProduct.
  3. It emits ImageMatchSuggested with candidates and confidence scores.
  4. The customer or an admin confirms the match; the confirmed item is attached to the order line before creation.

Key Relationships

  • One Customer → many Orders; one Order → exactly one Customer.
  • One Order → 1..100 OrderLines at intake; a line quantity up to 999,999.
  • One BulkPurchase → 1..500 BulkPurchaseLines.
  • Allocation is the many-to-many bridge between BulkPurchaseLine and OrderLine.

Scalability & Deployment

Stateless services

Auth/session state lives in tokens validated at the gateway; any replica serves any request.

Horizontal scaling

Kubernetes Deployments with replicas; HPA reacts to CPU/latency and Kafka consumer lag.

Kafka parallelism

Consumer groups; partition count sets max parallelism; aggregate-id keying preserves per-order ordering.

Idempotent consumers

At-least-once delivery made safe via a processed-event dedup table.

Shared database

One oms DB for all services (simpler for this stage); read-heavy paths can use short-TTL caches.

Object storage

Images in an S3-compatible bucket, keeping large binaries out of PostgreSQL.

Containers & orchestration

Docker images; Kubernetes with liveness/readiness probes and rolling updates.

Observability

Structured logs, Prometheus metrics, OpenTelemetry tracing across gateway → service → Kafka.

Mobile readiness

All access is REST/JSON through the gateway, so the later mobile app reuses the same backend with no server changes.

Testing Strategy

A dual approach: property-based tests for universal invariants and example/integration tests for specific scenarios and side effects.

Property-based (jqwik)

Intake validation, data-model invariants, allocation arithmetic/guards, lifecycle, duration computation, notification retry. Min 100 iterations each; boundary values generated deliberately.

Example (JUnit 5 + AssertJ)

Empty order list returns empty without error; nonexistent order returns not-found; a new order reports status Created.

Integration (Spring Boot + Testcontainers)

Notification within the 60s window (mock sender + controllable clock); after-commit Kafka publish with idempotent redelivery; image upload → match round trip with a stub VisionProvider.

Deferred Items

WhatsApp channel — order intake, communication, or notification through WhatsApp. The MVP supports website intake only.
Automated purchasing / platform API integrations — programmatic order placement on external platforms. The MVP supports manual bulk-purchase recording only.
Mobile application — a planned later milestone. The architecture already accommodates it: the mobile client reuses the same API Gateway and contracts, so no server-side redesign is required.
