OMS architecture — plain English

One shop, many small programs. Click a service below for a worked example.

Three ideas you need

Microservice — a small app with one job (orders, stock, delivery…). Each can start/stop alone.
Shared database — one oms notebook for all services (simpler for now). Each still owns its tables; they talk via API or events, not by editing each other’s rows ad hoc.
Kafka — a shared notice board. After saving data, a service posts “order created”; others read and react later.

How a request moves

You (browser) → Gateway → one service → shared DB. Side effects → Kafka → other services.

Pick a service — one example

One story across services

Alice orders 2 mice → gets notified

  1. intake validates + may run image match → asks order-service to save.
  2. order-service saves ORD-1001 → posts OrderCreated on Kafka.
  3. delivery-service hears it → status Created.
  4. allocation-service hears it → knows Alice needs 2 mice.
  5. Admin records bulk buy, receives stock, allocates 2 → OrderFullyAllocated.
  6. delivery-service → status Allocated.
  7. Admin marks delivered → Delivered_To_Customer + NotificationRequested.
  8. notification-service sends the message to Alice.

Why not one big app?

Each piece scales and fails alone. Kafka lets slow work (AI, email) happen without blocking the click. Tables stay grouped by service even though they live in one shared oms database.
