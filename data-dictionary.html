System architecture

Clients talk REST/JSON to one API Gateway. All Spring Boot services share one database (oms). After a successful commit, producers publish domain events directly to Kafka via DomainEventPublisher. Same diagram as design.html.

Shared: idempotency

Consumers that handle Kafka events use processed_event for dedupe. Producers publish directly after commit via DomainEventPublisher.

processed_event

FieldTypeConstraintsMeaning
eventKeyString (PK)topic + aggregate (+ version)Dedup key
processedAtInstantrequiredWhen first processed
How it is processed: Before handling a Kafka message, the consumer checks this table. If the key exists, the handler is a no-op. Otherwise the handler runs and the key is inserted. Makes at-least-once Kafka redelivery safe (no double allocation, double notify, etc.).

End-to-end processing flows

1. Customer order intake

  1. Client uploads image (optional) → intake validates JPEG/PNG ≤ 10 MB → object storage + after-commit ImageUploaded.
  2. image-analysis consumes event → VisionProvider → ImageMatchSuggested; user confirms itemRef.
  3. Client POST /api/orders → intake validates lines (1..100, qty, search/image) → calls order-service.
  4. order-service validates customer + items → writes customer_order, customer_order_line, then publishes OrderCreated.
  5. delivery-service inserts order_lifecycle (Created) + first status_transition_record.
  6. allocation-service seeds order_line_allocation_state rows for ceilings.

2. Bulk purchase → allocate

  1. Admin records bulk → bulk_purchase + bulk_purchase_line atomically.
  2. Admin marks received → updates receivedQty + publishes BulkPurchaseReceived.
  3. Admin allocates → insert allocation, update order_line_allocation_state.
  4. When all lines fully allocated → publish OrderFullyAllocated → delivery status Allocated + transition row.

3. Deliver → notify

  1. Admin marks order delivered (only if Allocated) → update order_lifecycle, append transition, publish delivered + NotificationRequested.
  2. notification-service upserts notification_record, sends with ≤ 3 retries → SENT or FAILED.
